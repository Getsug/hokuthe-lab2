## 3. `gcd(a, b)` design

**Signature:** `def gcd(a: int, b: int) -> int:`

**Docstring:** one short paragraph covering the behavior (Euclidean algorithm, iterative, non-negative result, `gcd(0, 0) == 0`), `a`/`b` as ints (negative and zero allowed), the return value, and `TypeError` for non-int input.

**Validation (Req 7), before any algorithm step:**
```
for value in (a, b):
    if not isinstance(value, int) or isinstance(value, bool):
        raise TypeError(...)
```
- `bool` is rejected explicitly because `bool` is a subclass of `int`.
- `float`, `str`, `None` and other types fail the `isinstance` check.
- The error message names the offending argument and its type, for example `gcd() arguments must be int, got float`.
- Both arguments are checked before any computation, so `gcd(2, 1.5)` and `gcd(1.5, 2)` both raise.
- The `for` loop over a 2-tuple is not recursion and adds only constant memory.

**Algorithm (Req 8), preserved exactly as written:**
```
a = abs(a)
b = abs(b)
while b != 0:
    a, b = b, a % b
return a
```
- If `a < b`, the first iteration gives `(a, b) = (b, a)`, because `a % b == a`. No ordering step is needed (8e).
- `gcd(0, 0)` skips the loop and returns 0. If one input is zero, the loop runs at most once (Req 11).
- Python's arbitrary-precision `int` handles values beyond 64 bits with no extra code.
- Memory: only `a` and `b` are kept, so O(1) extra memory. The iteration bound is the standard Euclidean/Lamé bound.

## 4. `__main__` test runner design

**Imports:** `import math` and `import sys` inside the block only (Req 10).

**Test data, as two literal tables (no helper functions, Req 5):**
- `gcd_cases`: a list of 15 tuples `(a, b, expected)` in the order of the requirements table (#1 to #15).
- `type_cases`: a list of 4 tuples `(a, b)` for `(1.5, 2)`, `("a", 2)`, `(None, 2)` and `(True, 2)` (#16 to #19).
- #15 uses expressions: `(2**100, 3 * 2**70, 2**70)`.

**Counters:** `passed = 0`, `total = 0`.

**GCD loop, for each `(a, b, expected)`:**
1. `result = gcd(a, b)`
2. `ok = (result == expected) and (result == math.gcd(a, b))`
3. Print `gcd({a}, {b}) = {result} (expected {expected}) PASS|FAIL`.
4. Update `total`, and update `passed` if `ok`.

**TypeError loop, for each `(a, b)`:**
1. `try: gcd(a, b)` then `ok = False`, with `except TypeError: ok = True`.
2. Any other exception type is not caught, so it propagates, crashes the script with a traceback and a nonzero status, and shows up in the output as a failure. That is acceptable here because only `TypeError` is correct.
3. Print `gcd({a!r}, {b!r}) raises TypeError (expected TypeError) PASS|FAIL`.
4. The `!r` format keeps the output readable and ASCII-safe: `'a'`, `None`, `1.5`, `True`.

**Summary and exit status:**
- Print `{passed}/{total} passed`.
- `sys.exit(0 if passed == total else 1)`.

**Output details:**
- ASCII only. Large values print as full integers (e.g. `1180591620717411303424`), with no thousands separators.
- Example lines:
  ```
  gcd(12, 8) = 4 (expected 4) PASS
  gcd(1.5, 2) raises TypeError (expected TypeError) PASS
  19/19 passed
  ```
- A `gcd` call that crashes with an unexpected exception inside the GCD loop is not caught, for the same reason as above.

## 7. Verification plan

1. Run the script and check the output and exit status 0 (19/19).
2. Run the script with a deliberately wrong expected value, in a temporary copy rather than the deliverable, to confirm a `FAIL` line and exit status 1.
3. Import test: `python -c "import gcd_iterative"` prints nothing.
4. Property check: a randomized comparison of `gcd` against `math.gcd` over a few thousand random integer pairs, including negatives and zero, run as a one-off command that is not part of the deliverable.
5. Review by reading the code: no recursion, no imports outside `__main__`, one public function.

## 8. Decisions and risks

- **Rejecting `bool`:** this makes `gcd(True, 2)` raise even though `True` is `1`. This is by requirement.
- **Unexpected exceptions in tests:** these crash the script instead of being recorded as `FAIL`. This keeps the runner free of helpers and broad `except` clauses. The failure mode is still a nonzero exit status.
- **Windows output encoding:** the ASCII-only output plus the explicit PowerShell encoding avoids the UTF-16 problem.
- **Python version:** the README records the version that actually ran, not the intended 3.14.7. If the local interpreter differs, the README says so.
